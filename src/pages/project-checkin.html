專案簡介

「簽到通」是我為聚豐整合行銷開發的活動出勤管理系統， 處理他們每年數十場到校巡迴演出與現場活動的排班、簽到與計薪。 2026 年 7 月上線，目前是他們實際在使用的系統。

先說清楚一件事：聚豐是我父母的公司。 這件事對這個案子的影響是——我拿得到一般接案很難拿到的東西： 完整的營運現場、所有沒被寫進需求文件的抱怨，以及上線之後長期而誠實的回饋。 這個系統不是交付完就結束，它每個月都還在被使用、被挑毛病。

原本的流程有多難

他們的活動分兩種，痛點也是兩種。

現場活動用紙本簽到。活動一忙就會忘了請人簽， 簽到單在收拾現場的混亂裡很容易不見——而那張紙是後續計薪的唯一依據。

到校巡迴的複雜度則是另一個層級。 一場活動要同時對齊：哪一間學校、什麼時間、教材要準備多少份、 工作人員有誰、演出人員有誰、現場志工有誰。 而這些欄位在活動前還會一直變動——有人臨時請假、有人被調去別場。

更關鍵的是，這套流程有兩個不能動的地方： 班表是 Excel，那是他們已經用了很久的工具，而且會反覆修改； 查驗單要列印出來給學校單位簽名，欄位與格式是規定好的，不能自己發明。

所以這個系統的限制條件從一開始就很清楚：
不能要求他們改變工作方式，只能把重複的部分自動化。

為什麼是 LINE

現場志工的年齡普遍偏大。 任何需要下載 App、註冊帳號、記住密碼的方案，對他們都是一道障礙—— 而且活動當天現場很忙，沒有人有空在門口教一位長輩怎麼註冊。

LINE 是他們本來就每天在用的東西，掃 QR code 也是他們已經熟悉的動作。 所以簽到端做成 LIFF（在 LINE 裡直接開啟的網頁）， 用 LINE 本身的身分辨識取代帳號密碼：

掃 QR → LINE 自動辨識身分 → 第一次使用時綁定本名 → 確認活動資訊 → 一鍵簽到。

簽到端在 LINE 裡開啟，不需要下載或註冊任何東西

「不用學新東西」聽起來不像一個設計決策，但它其實是這個案子最重要的一個。 技術上有更嚴謹的做法，但只要多一個註冊步驟，這套系統在現場就推不動。

怎麼組起來的

架構上我做了一個刻意的決定：沒有自建後端。 整套是純前端加上 Firebase，用原生 JavaScript ES Modules，沒有框架、沒有打包流程。

原因是使用者是一間中小型公司。我不想留下一個需要有人固定維運的東西給他們， 也不想讓自己變成那個唯一能維護它的人。 少一層自建服務，就少一個會在半夜壞掉、而且只有我修得好的環節。

後台分成四個模組：

  • 儀表板：統計卡與即時簽到動態流。用 Firestore 的即時監聽，現場有人簽到，畫面就跳一筆。
  • 活動管理：支援兩種計費型態——巡迴場採固定場費，單場則是角色 × 時薪 × 時數。
  • Excel 班表批次建立：上傳既有班表 → 選月份與日期 → 預覽當天所有場次與人力配置 → 一鍵建立活動與名單。
  • 薪資結算：依出勤自動計費，區分已付與待付，可依月份篩選並匯出 CSV。

上傳原本的 Excel 班表，系統直接預覽當天要建立的所有場次

第三個模組是整套系統裡我覺得最有價值的一段，因為它同時服務兩種完全不同的使用者： 內部人員要在幾分鐘內建好幾十場活動， 學校單位則要拿到一張格式正確、可以當場簽名的紙。

所以匯入之後會自動生成整批可列印的 A4 查驗單， 上面帶著該場的 QR code，教材數量依班級數與人數自動換算， 而且幼兒園與小學用的是不同版型。

自動生成的查驗單。QR code、教材數量、版型都依場次條件自動決定

現場的髒資料

真正花時間的不是把功能做出來，是處理現實。

系統實際跑起來之後才會遇到這些事：有人先簽到了，名字才被補進名單； 同一場活動裡出現兩個同名的人；名單上根本沒有的臨時人員直接出現在現場。

所以我寫了一段對帳邏輯，在名單更動時把既有的簽到紀錄依姓名對回本人； 同一個人有多筆時保留最早的那一筆，避免同一場被重複計薪。

這段程式本身不難。難的是知道它需要存在。

這也是我覺得「有一個真實在營運的客戶」最大的價值： 規格書上不會寫「會有人代打卡之外的十七種意外」， 那些只會在第三場活動結束後，用一通電話的形式出現。

取捨與已知限制

簽到端必須能在未登入的狀態下寫入資料，否則志工就得先登入—— 那就違背了「不用學新東西」這個前提。

所以權限是分層設計的：簽到紀錄開放寫入與單筆讀取， 但「列出全部」被鎖住，只有管理員能用；薪資資料則完全只有管理員可讀寫。 這樣擋得住匿名者整批下載個資，這是我最在意的一條線。

但它擋不住另一件事：知道活動 ID 的人可以寫入一筆假的簽到紀錄。 現階段這個風險由流程補起來——QR code 是現場工作人員當下發的， 而且每筆簽到都要對得上名單才會進入計薪。

我把它記為已知限制而不是漏看的洞。 下一步的處理方式是把寫入改走後端函式，或加上 App Check 做來源驗證。 在便利性與嚴謹之間，我這次選了前者，但知道帳要記在哪裡。

成果與現況

2026 年 7 月上線，目前是聚豐實際在使用的系統。

原本需要人工對照 Excel、追回紙本簽到單、再手動計算薪資的流程，現在變成一條線：

上傳班表 → 自動建立場次 → 列印查驗單 → 現場掃碼簽到 → 自動結算

我沒有辦法給出一個「省下幾小時」的精確數字，因為他們原本就沒有在計時。 但從「一疊可能會弄丟的紙本簽到單」到「後台按一次匯出」， 這個差距本身大概已經說明了問題。

薪資結算：依出勤自動計費，區分已付與待付，可匯出 CSV

基於系統目前裝載真實個資且仍在營運，這裡不公開部署網址。 需要實際操作示範的話，歡迎與我聯繫。
